# 7. Funkcjonalności wykraczające poza podstawowy zakres pracy (черновик, RU)

В процессе реализации функциональный объём системы вышел за пределы шести официально заявленных целей. Ниже описаны наиболее значимые дополнительные модули — не как второстепенные, а как самостоятельная часть инженерного результата работы, требующая отдельного описания.

## 7.1. Generowanie planów treningowych z wykorzystaniem AI

Сервис `GroqService` (`lib/services/groq_service.dart`, около 780 строк) интегрирует приложение с внешним API Groq — облачной платформой инференса больших языковых моделей, использующей специализированное аппаратное обеспечение (LPU) для сверхнизкой задержки ответа. В качестве модели используется `openai/gpt-oss-120b` с низким уровнем рассуждения (`reasoning_effort: low`); на ранних этапах проекта использовалась `llama-3.3-70b-versatile` (обоснование замены — раздел 5.1).

Для каждого из четырёх тренировочных направлений (Full Body, Powerlifting, Armwrestling, Streetlifting) определён детальный контекстный промпт, задающий приоритеты по мышечным группам и жёсткие правила отбора упражнений — например, для направления Powerlifting приседания, жим лёжа и становая тяга помечены как обязательные, если присутствуют в библиотеке упражнений пользователя. Результат генерации оборачивается в модель `AiSuggestedWorkout`, содержащую саму программу (`Workout`), текстовое обоснование выбора (`reasoning`) и метку времени генерации.

Важное проектное решение — AI не применяет план автоматически. Сгенерированная программа проходит через экран одобрения (`programs_screen.dart`), где пользователь может принять или отклонить предложение; при ошибке генерации (например, при недоступности сети или неверном ключе API) пользователю показывается явное сообщение об ошибке, а не тихий сбой. Таким образом реализована модель «человек в контуре» (human-in-the-loop) — искусственный интеллект выступает советчиком, а не автономным агентом, принимающим решения без контроля пользователя. Отдельный виджет `workout_ai_evaluation.dart` использует ту же модель для оценки уже выполненной тренировки.

Помимо генерации программ, языковая модель решает в системе ещё ряд узких задач, для которых детерминированный алгоритм был бы либо слишком громоздким, либо невозможным без больших справочных данных:

- **Оценка расхода калорий за тренировку** (`estimateWorkoutCalories`). Реализован гибридный подход: если для кардио-упражнения пользователь сам ввёл калории (например, с дисплея тренажёра), эти данные считаются точнее любой оценки и используются как есть, а модели отправляется только остаток тренировки — силовые упражнения (подходы, повторения, вес), упражнения с собственным весом и кардио без введённых калорий — с длительностью, из которой вычтено время уже учтённых кардио-подходов (во избежание двойного счёта). Итог равен сумме оценки модели и введённых пользователем значений. Оценка сохраняется в истории тренировки и используется в аналитике (раздел 6.5) и в модуле питания (раздел 7.4), где сожжённые на тренировке калории добавляются к суточной норме.
- **Генерация плана питания** (`generateNutritionPlan`) — дополняет детерминированный расчёт нормы калорий и макронутриентов (раздел 7.4) расписанием приёмов пищи.
- **Сопоставление упражнения с соревновательным движением** (`matchExerciseToRecord`). Чтобы сравнить результат пользователя с мировым рекордом IPF (раздел 7.3), нужно понять, является ли упражнение с произвольным пользовательским названием («Присед со штангой», «Low bar squat», «Жим лёжа соревновательный») одним из трёх соревновательных движений. Модели передаются явные правила (вариации — румынская тяга, присед с паузой, жим узким хватом — соревновательными не считаются), запрос выполняется с температурой 0.1, а ответ принимается только при уверенности модели не ниже 0.75 — в противном случае упражнение считается несопоставимым. Результат кешируется локально для каждого упражнения, так что запрос к API выполняется не более одного раза.
- **Оценка ранга при неполном профиле** (`estimateRankFromPartialProfile`) — когда данных для композитного алгоритма ранжирования (раздел 7.2) недостаточно, модель даёт грубую консервативную оценку с явной инструкцией смещаться к более низким рангам при нехватке доказательств.

Ко всем запросам к модели применены единые правила устойчивости: ограничение времени ожидания (от 10 до 25 секунд в зависимости от типа запроса), удаление markdown-обрамления ```` ``` ```` перед разбором JSON, а также хранение последней ошибки (`lastError`) в понятной пользователю форме — отсутствие ключа, ошибка API с кодом, превышение времени ожидания, некорректный ответ модели. В экране настроек AI (`ai_config_screen.dart`) добавлена проверка соединения (`testConnection`), отправляющая минимальный запрос и различающая типичные случаи: ключ работает, ключ неверен (HTTP 401), ключ верен, но превышен лимит запросов (HTTP 429). Это превращает неочевидную для пользователя проблему конфигурации внешнего сервиса в однозначное сообщение.

## 7.2. System rankingowy i grywalizacja

Система прогрессии реализована в двух взаимодополняющих сервисах. `RankService` вычисляет ранг пользователя напрямую относительно мирового рекорда в конкретном упражнении (`calculateRank(userBest, worldRecord)`, `percentOfWorldRecord`, `kgToNextRank`) — семь уровней от «деревянного» (wooden) до «алмазного» (diamond), визуализированных соответствующими иконками (`assets/images/*_rank.png`).

Более сложный алгоритм реализован в `RankingAlgorithm` (`lib/services/ranking_service.dart`) — композитная оценка, объединяющая четыре взвешенных компонента: силу (`strength`, вес 0.45, вычисляется только при наличии достаточного числа отслеживаемых упражнений), консистентность тренировок (`consistency`, вес 0.20), достижения (`achievement`, вес 0.15) и текущую динамику (`momentum`, вес 0.20). Итоговый линейный балл дополнительно преобразуется степенной функцией `100 × (linear / 100)^1.35`, что делает верхние ранги непропорционально труднодостижимыми — эффект, аналогичный принципу прогрессивной перегрузки (раздел 4.1), перенесённый в игровую механику. Из композитного балла также вычисляется примерная перцентиль пользователя (степенная кривая с показателем 1.8) и коэффициент уверенности в оценке (`confidence`), растущий с объёмом накопленных данных — при недостатке истории система честно понижает уверенность и опирается на эвристику, а не выдаёт вводящий в заблуждение точный ранг. Каждое присвоение ранга сопровождается текстовым объяснением (`_buildReason`), в духе того же принципа интерпретируемости, что и в адаптивном алгоритме нагрузки (раздел 6.2).

Систему дополняют достижения (`achievement_popup_service.dart`) и челленджи (`ChallengeService`) — соревнования между пользователями (обычно друзьями) по одной из пяти категорий: число тренировок, суммарный поднятый вес, результат в конкретном упражнении, серия тренировок, консистентность выполнения плана. Челленджи транслируются в реальном времени через потоки Firestore (активные/завершённые/ожидающие подтверждения) и поддерживают принятие и отклонение приглашения. Раздел челленджей реорганизован в общий экран (`challenges_hub_screen.dart`) с двумя вкладками: социальные челленджи с друзьями и персональные челленджи с видеофиксацией результата (раздел 7.7).

Перечень из 22 достижений (первая тренировка, 10/50/100/500 тренировок, суммарный поднятый вес 1/10/100 тонн, коэффициент Wilks 300/400, серии 7/30/100 дней, «ранняя пташка», «сова», первый друг и 10 друзей, победы в челленджах, «идеальная неделя», а также тематические — тренировка в Новый год и в день рождения) полностью локализован, причём числовые пороги в описаниях подставляются параметрами, а пороги по весу отображаются в выбранных пользователем единицах.

Коэффициенты относительной силы, используемые в достижениях и при сравнении атлетов разной массы тела, реализованы в `strength_coefficients.dart` по двум формулам: классической формуле Wilks (полином 5-й степени от массы тела в знаменателе) и более современной формуле DOTS (полином 4-й степени), обе в мужском и женском вариантах [ŹRÓDŁO: oficjalne współczynniki Wilks i DOTS — zweryfikować źródło]. Обе формулы покрыты модульными тестами с контрольными значениями.

## 7.3. Tablica liderów i porównanie ze światowymi rekordami IPF

Экран `community_leaderboard_screen.dart` предоставляет пять категорий рейтинга сообщества (число тренировок, суммарный вес, рекорд по выбранному упражнению, текущая серия, прогресс — в разработке), построенных на агрегированной коллекции `user_stats` в Firestore с учётом приватности (пользователь может скрыть себя из публичных рейтингов).

Уникальной особенностью системы является сопоставление результатов пользователя с реальными мировыми рекордами Международной федерации пауэрлифтинга (IPF). Serverless-функция в `functions/index.js` (Node.js, Firebase Cloud Functions v2, триггер по расписанию) обращается к открытому API портала openpowerlifting.org, последовательно запрашивая лучший результат по каждой комбинации пол × весовая категория × упражнение (приседание, жим лёжа, становая тяга) и сохраняя результат в Firestore. Эти данные затем используются `RankService` и экраном `stats_comparison_screen.dart` для отображения, например, «твой присед составляет 62 % от мирового рекорда в твоей весовой категории» — превращая абстрактный личный рекорд в объективно проверяемый показатель.

## 7.4. Moduł żywieniowy

`NutritionAlgorithmService.calculateTargets(...)` рассчитывает суточную норму калорий и макронутриентов на основе базового обмена веществ (BMR) по формуле Миффлина — Сан Жеора [ŹRÓDŁO: Mifflin M.D., St Jeor S.T. i wsp. — zweryfikować dokładne dane bibliograficzne przed użyciem]:

```
BMR (мужчины) = 10 × вес(кг) + 6.25 × рост(см) − 5 × возраст + 5
BMR (женщины) = 10 × вес(кг) + 6.25 × рост(см) − 5 × возраст − 161
```

Полученное значение BMR умножается на коэффициент активности, определяемый числом тренировочных дней в неделю (от 1.2 при отсутствии тренировок до 1.9 при семи тренировках в неделю), что даёт общий суточный расход энергии (TDEE), к которому добавляется поправка на цель пользователя (набор/удержание/снижение массы) в пределах безопасного диапазона (ограничено снизу и сверху — от 1200 до 6000 ккал). Из итогового значения калорий далее вычисляется распределение по белкам, жирам и углеводам (`MacroTargets`). Модуль представлен экранами `nutrition_screen.dart` и `nutrition_goal_screen.dart` и моделью `nutrition_profile.dart`.

## 7.5. Personalizacja, lokalizacja wielojęzyczna i onboarding

Приложение поддерживает три языка интерфейса — английский, польский и русский (`lib/l10n/app_en.arb`, `app_pl.arb`, `app_ru.arb`) через встроенный механизм локализации Flutter.

На раннем этапе проекта значительная часть текстов интерфейса была «зашита» в код на английском языке (в том числе в класс констант `app_strings.dart`), а текстовые обоснования рекомендаций алгоритма (раздел 6.2) и статусы восстановления мышц (раздел 6.4) генерировались прямо в сервисах в виде английских строк. В ноябре 2026 г. была выполнена полная миграция: класс `app_strings.dart` удалён, а все строки вынесены в ARB-файлы — на момент написания каждый из трёх файлов содержит **1050 ключей**, полностью синхронизированных между языками. Основные инженерные аспекты миграции:

- **Плюральные формы через ICU MessageFormat.** В русском и польском языках форма существительного зависит от числа нетривиально: «1 упражнение / 3 упражнения / 5 упражнений / 21 упражнение», «1 seria / 4 serie / 5 serii / 22 serie». Наивная конкатенация числа и слова здесь неизбежно даёт ошибки, поэтому все счётные строки (подходы, повторения, упражнения, дни) описаны конструкцией `{count, plural, one{...} few{...} many{...} other{...}}`, а выбор формы выполняет генератор по правилам CLDR.
- **Локализация вне дерева виджетов.** Обычный доступ к строкам во Flutter (`AppLocalizations.of(context)`) требует `BuildContext`, которого нет в сервисах бизнес-логики — например, в `ProgressionService`, формирующем текстовое обоснование рекомендации. Для этого введён лёгкий глобальный доступ `L10n.current`, который синхронизируется с выбранным языком в `SettingsService` при загрузке и каждом изменении настроек. Аналогично глобальный `Units.current` предоставляет сервисам текущие единицы измерения, благодаря чему, например, обоснование «прогресс — +5.5 lb» формируется сразу в фунтах.
- **Автоматическая проверка целостности переводов.** Тест `l10n_test.dart` разбирает ARB-файлы и проверяет, что польский и русский файлы содержат ровно тот же набор ключей, что и английский (нет ни пропущенных, ни лишних ключей), и что в каждой строке совпадает набор параметров-заполнителей (`{count}`, `{name}` и т. д.) — пропущенный заполнитель в переводе иначе проявился бы только во время выполнения. Отдельные тесты проверяют правильность плюральных форм на контрольных числах (1, 3, 5, 21 для русского; 1, 4, 5, 22 для польского).

**Единицы измерения.** Пользователь может выбрать систему единиц для веса (кг / фунты) и длины (см / футы и дюймы). Как описано в разделе 5.3, это чисто презентационная настройка: класс `Units` (`lib/utils/units.dart`) конвертирует значения при отображении и вводе, а хранение остаётся метрическим. Корректность конвертации, обработка некорректного ввода, сохранение знака у разницы весов и отсутствие погрешности при повторном сохранении неизменённого значения проверены модульными тестами (`units_test.dart`).

Тема оформления настраивается пользователем через `ThemeService`/`AppColor` (реализация Provider поверх `ChangeNotifier`, аналогично остальным сервисам приложения). Для новых пользователей предусмотрен интерактивный обучающий тур (`TourService`, `tour_overlay.dart`), знакомящий с основными разделами приложения при первом запуске.

## 7.6. Społecznościowy sklep programów treningowych (Store)

Функция «Друзья» (раздел 6.6) позволяет делиться прогрессом с узким кругом знакомых, но не решает другой практической задачи: опытный атлет или тренер составил хорошую программу и хочет, чтобы ей могли воспользоваться другие. Для этого реализован общедоступный магазин программ — вкладка «Store» на экране программ (`store_screen.dart`), экран публичной программы (`public_program_screen.dart`) и сервис `PublicProgramService`. С архитектурной точки зрения это первый модуль системы, в котором данные одного пользователя становятся доступны всем пользователям, что потребовало модерации контента и наиболее строгих правил безопасности в проекте (раздел 5.4).

**Публикация.** Из мастерской (раздел 6.3) автор отправляет программу через форму публикации (`publish_program_sheet.dart`), указывая название, описание, категорию (Full Body, Powerlifting, Armwrestling, Streetlifting, другое) и язык. Перед отправкой программа очищается: рабочие веса обнуляются, а в документ дополнительно записывается вычисленный список задействованных мышечных групп — для отображения в каталоге без разбора всей программы.

**Жизненный цикл и модерация.** Каждая публикация проходит через конечный автомат состояний:

```
            отправка                одобрение
  (нет) ───────────▶ pending ───────────────▶ approved ──┐
                       ▲   │                     │       │ обновление
                       │   │ отклонение          │       │ (снова pending)
   повторная отправка  │   ▼                     │       │
                       └─ rejected               ▼       │
                                            снятие ◀─────┘
```

Новая и повторно отправленная программа всегда попадает в статус `pending` — это обеспечивается не клиентским кодом, а правилами безопасности Firestore, так что обойти модерацию модифицированным клиентом невозможно. Модератор (в текущей версии — автор системы) переводит программу в `approved` или `rejected` с указанием причины отклонения, работая непосредственно в консоли Firebase. При следующем запуске приложения автор однократно видит диалог с результатом модерации (`moderation_result_dialog.dart`), после чего приложение помечает результат как просмотренный (`authorNotified = true`). Отклонённую программу можно исправить и отправить повторно, одобренную — обновить (что снова отправляет её на модерацию) или снять с публикации; при снятии уже сделанные другими пользователями копии сохраняются, так как после копирования программа принадлежит скопировавшему. В действия мастерской не включается публикация встроенных программ приложения и программ, скопированных из магазина (поле `sourcePublicId`), — чтобы пользователь не мог выдать чужую программу за свою.

Серверные триггеры Cloud Functions дополняют этот процесс: `onProgramReviewed` при смене статуса проставляет серверное время проверки и сбрасывает причину отклонения у одобренной программы, а `onProgramDeleted` рекурсивно удаляет подколлекцию маркеров скачиваний (Firestore не удаляет подколлекции вместе с родительским документом). Модуль спроектирован так, что основной сценарий работает и без этих функций — они лишь поддерживают чистоту данных. [уточнить: развёрнуты ли функции — см. раздел 5.1.]

**Каталог.** Магазин показывает только одобренные программы с фильтром по категории и двумя вариантами сортировки — по популярности (число скачиваний, при равенстве — по дате) и по новизне. Каталог загружается постранично по 20 программ с курсорной пагинацией (`startAfterDocument`), что сохраняет постоянную стоимость запроса независимо от размера каталога. Запросы магазина намеренно выполняются только к серверу (`Source.server`), минуя локальный кеш Firestore: показ устаревшей копии каталога офлайн мог бы привести к попытке скопировать уже снятую программу. Сетевые ошибки и превышение времени ожидания (12 секунд) преобразуются в единое исключение `StoreOfflineException`, по которому интерфейс показывает понятное сообщение об отсутствии соединения. Экран публичной программы показывает её состав и панель нагрузки на мышечные группы (раздел 6.3), чтобы пользователь мог оценить баланс программы до копирования.

**Копирование и слияние библиотек упражнений.** Нетривиальная инженерная задача возникает при копировании: программа ссылается на упражнения из библиотеки *автора*, а у копирующего пользователя есть своя библиотека — частично совпадающая (встроенные упражнения), частично нет (собственные упражнения автора), причём одно и то же упражнение могло быть переименовано. Наивное копирование либо дублировало бы упражнения («Жим лёжа» ×2 в библиотеке), либо ошибочно связывало бы разные упражнения с совпадающим идентификатором. Чистая функция `planWorkoutImport` (`lib/utils/workout_import.dart`) решает задачу в три шага для каждого упражнения программы (включая альтернативные упражнения):

1. совпадает идентификатор **и** нормализованное название (обрезка пробелов, нижний регистр, схлопывание пробелов) — используется существующее упражнение пользователя;
2. иначе, если совпадает нормализованное название — используется упражнение пользователя с этим названием (тот же идентификатор, но другое название означает, что пользователь отредактировал встроенное упражнение, и такое совпадение намеренно не засчитывается);
3. иначе упражнение добавляется в библиотеку пользователя с новым идентификатором, сохраняя описание и мышечные группы.

Результаты кешируются внутри одного импорта, поэтому упражнение, встречающееся в программе дважды (например, как основное и как альтернатива), добавляется один раз. Скопированная программа получает новый идентификатор, ссылку на источник (`sourcePublicId`) и нулевые веса — рабочий вес пользователю подберёт адаптивный алгоритм (раздел 6.2) по его собственной истории. Функция покрыта девятью модульными тестами, охватывающими все перечисленные случаи.

**Счётчик скачиваний** увеличивается клиентом в одной атомарной пакетной записи вместе с созданием маркера `downloads/{uid}`, а правила безопасности гарантируют ровно +1 и не более одного раза на пользователя (раздел 5.4). Такое решение не требует серверного кода и одновременно защищает рейтинг популярности от накрутки.

## 7.7. Personalne wyzwania z rejestracją wideo i rozpoznawaniem pozy (computer vision)

Последним по времени модулем системы стали персональные челленджи с видеофиксацией и распознаванием позы человека камерой смартфона. Мотивация двоякая: во-первых, для упражнений с собственным весом (отжимания) единственная объективная мера результата — число корректно выполненных повторений, а самоотчёт пользователя легко завышается; во-вторых, распознавание позы открывает путь к автоматическому подсчёту повторений и контролю техники — функциям, которых нет ни в одном из рассмотренных в главе 4 приложений [уточнить по таблице 4.3].

**Персональные челленджи.** Для отжиманий определена лестница из семи целей — 10, 25, 50, 100, 250, 500 и 1000 повторений, — каждая из которых сопоставлена с одним из семи рангов системы грейдов (от «деревянного» до «алмазного», раздел 7.2), так что персональные челленджи визуально и концептуально встроены в общую систему прогрессии. Сервис `PersonalChallengeService` хранит лучший результат пользователя локально и засчитывает попытку только при его улучшении; цель считается выполненной, если лучший результат не меньше целевого числа повторений.

**Камера и распознавание позы в реальном времени.** Экран попытки (`pose_camera_screen.dart`) получает поток кадров с фронтальной или тыловой камеры (с возможностью переключения) в формате YUV420 и для каждого кадра запускает детектор позы из пакета `pose_detection`, возвращающий 33 ключевые точки тела с координатами и показателем видимости. Поверх изображения с камеры отрисовывается «скелет» обнаруженной позы. Основные инженерные решения:
- **Обработка кадров без очереди.** Если предыдущий кадр ещё обрабатывается (флаг `_frameInFlight`), новый кадр отбрасывается, а не ставится в очередь, — так задержка отображения не накапливается на медленных устройствах, а снижается лишь частота обновления (текущее значение FPS выводится на экран).
- **Ограничение разрешения**: кадр перед инференсом масштабируется так, чтобы большая сторона не превышала 640 пикселей, с учётом ориентации сенсора и зеркалирования фронтальной камеры.
- **Устойчивая инициализация модели**: сначала используется скомпилированная модель с точностью FP16 (быстрее на устройствах с поддержкой ускорения), при неудаче — стандартный интерпретатор TFLite.
- **Жизненный цикл**: при сворачивании приложения запись корректно останавливается и камера освобождается, при возврате — переинициализируется; отказ в разрешении на камеру распознаётся отдельно и показывается понятным сообщением.
- **Запись видео параллельно с анализом**: во время записи попытки поток кадров продолжает поступать в детектор (`startVideoRecording(onAvailable: ...)`), а на устройствах, где это не поддерживается, запись выполняется без анализа. Видео сохраняется в каталог приложения и может быть просмотрено сразу после попытки.

Все вычисления выполняются **на устройстве**: видео тренирующегося человека не отправляется ни на какой сервер, что принципиально с точки зрения приватности.

**Геометрия суставов.** Модуль `pose_geometry.dart` вычисляет углы в суставах по трём ключевым точкам как угол между векторами BA и BC:

```
θ = arccos( (BA · BC) / (|BA| · |BC|) ) · 180 / π
```

Определены четыре угловые метрики: локоть (плечо–локоть–запястье), линия корпуса (плечо–таз–лодыжка; для отжиманий значение, близкое к 180°, означает прямое тело без прогиба), колено (таз–колено–лодыжка) и тазобедренный сустав (плечо–таз–колено). Поскольку при съёмке сбоку одна сторона тела частично закрыта, метрика вычисляется для левой и правой стороны отдельно; сторона, у которой хотя бы одна точка имеет видимость ниже 0.5, отбрасывается, а из двух валидных выбирается сторона с большей суммарной видимостью.

**Инструмент сбора размеченного датасета.** Автоматический подсчёт повторений и оценка их корректности требуют порогов (например, «повторение засчитывается, если угол в локте опустился ниже X° и затем вернулся выше Y° при линии корпуса не менее Z°»), которые нельзя честно взять «из головы». Поэтому сначала был создан внутренний инструмент разработчика (`lib/dev_test/`), предназначенный для сбора эмпирических данных:
- запись попытки (отжимания или приседания) с указанием ракурса съёмки — сбоку, спереди или под 45°;
- одновременное сохранение видео и покадрового следа позы — для каждого кадра метка времени и 33 точки × (x, y, z, видимость), с округлением для компактности JSON-файла;
- экран просмотра, синхронизирующий воспроизведение видео с графиками угловых метрик во времени (`fl_chart`) — с ручной подстройкой смещения между видео и следом позы, бинарным поиском кадра по времени и выводом диапазона углов (минимум … максимум) за попытку;
- ручная разметка: разработчик просматривает запись и указывает общее число повторений и число технически корректных, после чего запись помечается как одобренная; сводка показывает, сколько корректных повторений собрано для каждой комбинации «упражнение × ракурс».

Таким образом, порог для будущего счётчика повторений будет выведен из размеченных данных, а точность счётчика — измерена на них же (сравнение автоматического подсчёта с ручной разметкой), а не заявлена без проверки. **Текущий статус**: распознавание позы, запись и сбор датасета реализованы; автоматический подсчёт повторений на экране попытки пока не включён (счётчик отображается как «— / цель»).
