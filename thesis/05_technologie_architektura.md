# 5. Technologie i architektura systemu (черновик, RU)

## 5.1. Stos technologiczny i uzasadnienie wyboru

Как уже упоминалось во введении, фактически реализованный технологический стек отличается от заявленного в первоначальном техническом задании (Node.js/Express, PostgreSQL, Riverpod/Bloc, Firebase Cloud Messaging). Ниже приведён фактический стек и обоснование каждого решения.

**Клиентское приложение — Flutter (Dart).** Выбор совпадает с исходным брифом: Flutter позволяет вести разработку из единой кодовой базы с полноценным доступом к нативным возможностям Android, что для одного разработчика критично с точки зрения скорости итераций (hot reload) и отсутствия необходимости дублировать логику на двух платформах.

**Управление состоянием — Provider вместо Riverpod/Bloc.** Provider реализует классический паттерн `ChangeNotifier`/`Consumer` и требует существенно меньше шаблонного кода и настройки, чем Bloc (явное разделение events/states) или Riverpod (кодогенерация, отдельная модель провайдеров). При соло-разработке и объёме проекта, не требующем сложной многоуровневой композиции состояний, Provider обеспечивает достаточную реактивность интерфейса при заметно более низком пороге входа и более быстрой разработке новых экранов.

**Локальное хранение — SharedPreferences.** Основные данные пользователя (упражнения, тренировочные программы, история тренировок, настройки) хранятся локально в виде сериализованных JSON-записей. Это решение принципиально важно для приложения такого класса: тренировка часто проходит в помещении с плохим или отсутствующим интернет-соединением (спортзал в подвале, поле и т. д.), поэтому основной пользовательский сценарий — просмотр программы и логирование подходов — обязан работать полностью офлайн.

**Бэкенд — Firebase (Firestore, Authentication, Cloud Functions) вместо Node.js/Express + PostgreSQL.** Функции, требующие облачной синхронизации между устройствами и пользователями — профиль, статистика для лидерборда, заявки в друзья, челленджи, публичный магазин программ (раздел 7.6) — реализованы поверх Cloud Firestore, документоориентированной базы данных реального времени. Ключевые причины отказа от классической связки Express + PostgreSQL: (1) Firestore из коробки предоставляет потоковую (`Stream`) подписку на изменения данных, что напрямую используется в лидерборде и списке челленджей без необходимости реализовывать WebSocket-слой вручную; (2) Firebase Authentication снимает с разработчика задачу безопасного хранения паролей и управления сессиями; (3) отсутствие необходимости администрировать и оплачивать отдельный сервер и реляционную СУБД существенно снижает эксплуатационную нагрузку на проект, выполняемый одним человеком в рамках дипломной работы. При этом Node.js из исходного брифа не был полностью отброшен: он используется в виде serverless-функций Cloud Functions (`functions/index.js`) для фоновых задач, не привязанных к клиентским запросам — в частности, для периодического обновления мировых рекордов IPF (раздел 7.3), а также для триггеров Firestore (`onDocumentUpdated`, `onDocumentDeleted`), обслуживающих модерацию и удаление публичных программ (раздел 7.6). [уточнить: развёрнуты ли функции в продакшене — проект Firebase работает на бесплатном тарифе Spark, на котором развёртывание Cloud Functions недоступно без перехода на тариф Blaze; если функции так и не были развёрнуты, это нужно честно указать здесь и в главе 10, а модуль магазина спроектирован так, что работает и без них — см. раздел 7.6.]

**Push- и локальные уведомления — flutter_local_notifications вместо Firebase Cloud Messaging.** Заявленный в брифе FCM предполагает серверный триггер отправки push-уведомлений (например, «твой друг только что побил твой рекорд»). В текущей реализации уведомления (напоминания о тренировке, о заполнении опросника самочувствия) генерируются и планируются локально на устройстве средствами `flutter_local_notifications` и `timezone`, без необходимости серверной инфраструктуры для доставки сообщений. Это ограничивает набор возможных уведомлений only локальными/расписанными сценариями и отмечено как направление дальнейшего развития (раздел 10).

**Внешний AI-сервис — Groq API (модель `openai/gpt-oss-120b`).** Для генерации и оценки тренировочных планов используется языковая модель, доступная через Groq API — облачную платформу инференса, известную крайне низкой задержкой ответа благодаря специализированному аппаратному обеспечению (LPU). На ранних этапах разработки использовалась модель `llama-3.3-70b-versatile`; в ноябре 2026 г. сервис был переведён на открытую модель `openai/gpt-oss-120b` с параметром `reasoning_effort: low` — модель с режимом рассуждения даёт более стабильный структурированный JSON-ответ, а низкий уровень рассуждения удерживает задержку в пределах, приемлемых для мобильного интерфейса. Благодаря тому, что Groq предоставляет OpenAI-совместимый интерфейс, смена модели свелась к изменению одной константы (`_model`) без переписывания логики сервиса. Обучение собственной модели рекомендаций с нуля не рассматривалось: во-первых, у соло-разработчика нет доступа к достаточному объёму размеченных тренировочных данных для полноценного обучения; во-вторых, готовая крупная языковая модель с точно сформулированным по каждому тренировочному направлению промптом (раздел 7.1) решает задачу генерации персонализированного плана без необходимости собственной инфраструктуры машинного обучения — подход, прагматичный для инженерного проекта такого масштаба.

**Компьютерное зрение на устройстве — `camera` + `pose_detection`.** Для модуля персональных челленджей с видеофиксацией (раздел 7.7) используется пакет `camera` (поток кадров в формате YUV420 и одновременная запись видео) и пакет `pose_detection`, выполняющий оценку позы человека (33 ключевые точки тела с координатами и показателем видимости) локально на устройстве на основе модели TensorFlow Lite. Инференс выполняется без отправки кадров на сервер — это одновременно решение проблемы приватности (видео тренирующегося человека не покидает телефон) и проблемы задержки. Детектор инициализируется в режиме скомпилированной модели с точностью FP16, а при неудаче автоматически откатывается на стандартный интерпретатор. Сопутствующие пакеты: `video_player` (покадровый просмотр записанных попыток) и `path_provider` (хранение видео и разметки в файловой системе приложения).

**Визуализация и вспомогательные библиотеки.** Графики прогресса реализованы с помощью `fl_chart`, календарь тренировок — с помощью `table_calendar`. Интерактивная анатомическая карта тела (разделы 6.4, 6.5) реализована без сторонних SVG-библиотек: контуры мышц хранятся в коде как строки путей SVG, разбираются собственным минимальным парсером (`parseSvgPath`, команды M/L/C/Q/Z) в объекты `Path` Flutter и отрисовываются через `CustomPainter`; статический файл `assets/images/body_map.svg` генерируется из тех же данных отдельным скриптом `tool/generate_body_map_svg.dart`, что гарантирует единый источник истины для геометрии.

**Локализация — генератор `gen-l10n` (ARB + ICU).** Локализация реализована штатным генератором Flutter: строки хранятся в файлах `.arb` (формат на основе JSON с поддержкой синтаксиса ICU MessageFormat для плюральных форм и параметров), а типизированный класс `AppLocalizations` генерируется автоматически в `lib/l10n/generated/` (каталог исключён из системы контроля версий как производный артефакт). Подробнее — раздел 7.5.

## 5.2. Architektura systemu

Система имеет клиент-серверную архитектуру со смешанной (гибридной) моделью хранения данных.

Приложение построено по слоистой архитектуре: `models/` содержат неизменяемые классы данных с сериализацией (`toJson`/`fromJson`), `services/` инкапсулируют бизнес-логику и обращения к внешним источникам данных (27 сервисов), `screens/` отвечают за представление и пользовательское взаимодействие (39 экранов), `widgets/` — переиспользуемые компоненты интерфейса (19 файлов, включая подмодуль `widgets/body_map/` с анатомической картой тела), `utils/` — чистые вспомогательные функции без состояния (конвертация единиц измерения, импорт программ, форматирование), удобные для модульного тестирования. Отдельно выделен каталог `lib/dev_test/` — внутренний инструмент разработчика для сбора размеченных видеозаписей упражнений (раздел 7.7), не являющийся частью пользовательского сценария. По состоянию на ноябрь 2026 г. кодовая база клиента насчитывает около 40 000 строк кода на Dart (≈37 100 непустых) в 129 файлах (без учёта автоматически сгенерированных файлов локализации). Слой `services` расширяет `ChangeNotifier`, что делает его совместимым с моделью реактивности Provider: изменение данных в сервисе автоматически вызывает перестроение подписанных на него виджетов.

Данные разделены на две категории по принципу «где действительно нужна облачная синхронизация»: тренировочные данные (упражнения, программы, история тренировок, опросник самочувствия) хранятся локально и не требуют сети для основного сценария использования; данные, значимые для нескольких пользователей одновременно (профиль для лидерборда, заявки в друзья, статус челленджей), синхронизируются через Firestore в реальном времени.

## 5.3. Model danych

**Локальные модели (SharedPreferences, сериализация JSON):**
- `Exercise` — упражнение: название, описание, сложность, список задействованных мышечных групп с ролью (основная/вторичная/стабилизатор — используется трекером восстановления, раздел 6.4).
- `Workout` / `WorkoutExercise` — тренировочная программа и входящие в неё упражнения с целевым числом подходов, повторений, весом и опциональным альтернативным упражнением.
- `TrainingPlan` / `ScheduledWorkout` — расписание тренировок с поддержкой периодичности: каждая запись хранит дни недели, частоту в неделях и смещение недели, что позволяет реализовывать не только простое «через день», но и чередующиеся схемы (например, программа A/B через неделю).
- `WorkoutHistory` / `WorkoutSession` / `ExerciseResult` / `ExerciseSetResult` — завершённая тренировка: дата, длительность, результаты по каждому упражнению (фактически выполненные подходы и повторения), а также опциональная текстовая заметка пользователя к тренировке (`note`) и оценка сожжённых калорий (`estimatedCalories`, раздел 7.1). Для кардио-подходов результат подхода дополнительно хранит длительность в минутах (`durationMinutes`) и, если пользователь ввёл её вручную (например, с табло беговой дорожки), количество калорий (`calories`).
- `Workout.sourcePublicId` — необязательная ссылка на публичную программу из магазина, из которой была скопирована данная программа (раздел 7.6); используется, в частности, чтобы запретить повторную публикацию чужой программы от своего имени.
- `WellnessEntry` — запись опросника самочувствия: временная метка и набор числовых ответов на вопросы.
- `BodyMeasurementEntry` — замер одного из десяти обхватов тела (плечи, грудь, а также левые и правые бицепс, предплечье, бедро и икра) в сантиметрах с датой замера; хранится в `ProfileService` как словарь «тип замера → последнее значение».
- Лучший результат в персональных челленджах (`PersonalChallengeService`, раздел 7.7) — по одному целому числу на упражнение.
- `AppSettings` — пользовательские настройки (тема, язык, приватность, единицы измерения веса и длины).

Принципиальное решение для единиц измерения: **все величины хранятся строго в метрической системе** (килограммы, сантиметры), а пересчёт в фунты/дюймы выполняется исключительно на уровне отображения и ввода классом `Units` (`lib/utils/units.dart`). Благодаря этому переключение единиц в настройках не изменяет ни одной сохранённой записи, алгоритмы (раздел 6.2) всегда работают в килограммах, а при редактировании ранее введённого значения, которое пользователь не менял, возвращается исходное значение в килограммах без погрешности двойного пересчёта (кг → фунты → кг) — этот случай отдельно покрыт модульным тестом.

**Файлы на устройстве (вне SharedPreferences):** видеозаписи попыток в персональных челленджах и, во внутреннем инструменте разработчика, JSON-файлы с покадровой разметкой ключевых точек тела (раздел 7.7). Такие данные слишком объёмны для SharedPreferences и сохраняются в каталог приложения через `path_provider`.

**Облачные коллекции (Cloud Firestore):**
- `users/{userId}` — профиль пользователя, с подколлекциями `friends`, `workouts`/`workout_sessions` (реплика для доступа друзьями в рамках челленджей), `achievements`, `wellness_entries`.
- `user_stats` — агрегированная статистика для лидерборда (число тренировок, суммарный поднятый вес, текущая серия, персональные рекорды по упражнениям, флаг скрытия профиля).
- `friendRequests` — заявки в друзья (отправитель, получатель, статус).
- `world_records` — кешированные мировые рекорды IPF, обновляемые по расписанию Cloud Function (раздел 7.3); только для чтения со стороны клиента.
- `public_programs/{authorId}_{workoutId}` — публичные программы магазина (раздел 7.6): автор, псевдоним, название, описание, категория, язык, «очищенная» копия программы (без рабочих весов), список задействованных мышечных групп, статус модерации (`pending`/`approved`/`rejected`), причина отклонения, счётчик скачиваний. Детерминированный идентификатор документа (UID автора + идентификатор локальной программы) гарантирует, что одна локальная программа соответствует не более чем одной публикации — повторная отправка перезаписывает документ, а не создаёт дубликат. Подколлекция `downloads/{userId}` хранит по одному маркеру на каждого пользователя, скопировавшего программу.
- `admins/{userId}` — список администраторов-модераторов; наличие документа даёт права модерации в правилах безопасности.

Для запросов магазина (фильтрация по статусу и категории с сортировкой по популярности или дате) определены составные индексы в `firestore.indexes.json`; поля с крупным содержимым (`workout`, `description`) явно исключены из индексации, что уменьшает объём индексов и стоимость записи.

## 5.4. Bezpieczeństwo i prywatność danych

Аутентификация реализована через Firebase Authentication (email/пароль); ни один пароль или иной секрет не хранится в коде приложения или локальном хранилище. Доступ к данным в Firestore регулируется декларативными правилами безопасности (`firestore.rules`), построенными на принципе владения (`isOwner`): пользователь может читать и изменять только собственные данные, за исключением специально предусмотренных случаев. В частности, подколлекции `workouts` и `workout_sessions` открыты на чтение для друзей пользователя — это осознанное решение, обеспечивающее корректный подсчёт результатов в системе челленджей (раздел 7.2), где для сравнения нужны фактические тренировочные данные другого участника. Опросник самочувствия (`wellness_entries`), напротив, полностью приватен и не открывается даже друзьям. Дополнительно предусмотрен явный пользовательский переключатель `isProfileHidden`, скрывающий профиль из публичных запросов лидерборда независимо от факта дружбы.

Магазин программ (раздел 7.6) стал первым в системе случаем, когда данные, созданные одним пользователем, становятся доступны **всем** пользователям, — поэтому правила для коллекции `public_programs` спроектированы по принципу «клиенту не доверяем ничего»:
- **Чтение**: одобренные программы видны всем авторизованным пользователям; программы в статусе ожидания или отклонённые — только их автору и администратору.
- **Создание и повторная отправка**: функция `validSubmission` проверяет точный набор полей документа (`keys().hasOnly(...)`), совпадение автора с `request.auth.uid`, соответствие идентификатора документа шаблону `{uid}_{sourceWorkoutId}`, то, что статус равен `pending`, причина отклонения и дата проверки пусты, время создания равно серверному времени запроса (`request.time`), а также ограничения длины (название ≤ 60 символов, описание ≤ 500, псевдоним ≤ 40) и допустимый перечень категорий. Тем самым клиент технически не может опубликовать программу сразу в статусе «одобрена» или «накрутить» себе счётчик скачиваний при повторной отправке.
- **Подтверждение просмотра результата модерации**: автор может изменить ровно одно поле — `authorNotified` — и только на `true` (`diff(...).affectedKeys().hasOnly([...])`).
- **Счётчик скачиваний**: любой пользователь, кроме автора, может увеличить `downloadCount` строго на единицу и только в одной атомарной пакетной записи (batch) вместе с созданием собственного маркера `downloads/{uid}`; правило использует пару функций `exists()` / `existsAfter()` («маркера не было до записи и он есть после»), а правило для маркера — симметрично `get()` / `getAfter()`. Это гарантирует ровно одно засчитанное скачивание на пользователя без серверного кода.
- **Модерация**: изменение статуса разрешено только администратору (`isAdmin()` — наличие документа в коллекции `admins`); в текущей версии модерация выполняется вручную через консоль Firebase.

Дополнительно, на уровне приложения перед публикацией программа «очищается» (`PublicProgram.sanitizeWorkout`): рабочие веса всех упражнений обнуляются. Веса — это персональные данные о физической форме автора, и, кроме того, они не имеют смысла для другого пользователя, которому адаптивный алгоритм (раздел 6.2) в любом случае подберёт нагрузку по его собственной истории.
