# 5. Technologie i architektura systemu (черновик, RU)

## 5.1. Stos technologiczny i uzasadnienie wyboru

Как уже упоминалось во введении, фактически реализованный технологический стек отличается от заявленного в первоначальном техническом задании (Node.js/Express, PostgreSQL, Riverpod/Bloc, Firebase Cloud Messaging). Ниже приведён фактический стек и обоснование каждого решения.

**Клиентское приложение — Flutter (Dart).** Выбор совпадает с исходным брифом: Flutter позволяет вести разработку из единой кодовой базы с полноценным доступом к нативным возможностям Android, что для одного разработчика критично с точки зрения скорости итераций (hot reload) и отсутствия необходимости дублировать логику на двух платформах.

**Управление состоянием — Provider вместо Riverpod/Bloc.** Provider реализует классический паттерн `ChangeNotifier`/`Consumer` и требует существенно меньше шаблонного кода и настройки, чем Bloc (явное разделение events/states) или Riverpod (кодогенерация, отдельная модель провайдеров). При соло-разработке и объёме проекта, не требующем сложной многоуровневой композиции состояний, Provider обеспечивает достаточную реактивность интерфейса при заметно более низком пороге входа и более быстрой разработке новых экранов.

**Локальное хранение — SharedPreferences.** Основные данные пользователя (упражнения, тренировочные программы, история тренировок, настройки) хранятся локально в виде сериализованных JSON-записей. Это решение принципиально важно для приложения такого класса: тренировка часто проходит в помещении с плохим или отсутствующим интернет-соединением (спортзал в подвале, поле и т. д.), поэтому основной пользовательский сценарий — просмотр программы и логирование подходов — обязан работать полностью офлайн.

**Бэкенд — Firebase (Firestore, Authentication, Cloud Functions) вместо Node.js/Express + PostgreSQL.** Функции, требующие облачной синхронизации между устройствами и пользователями — профиль, статистика для лидерборда, заявки в друзья, челленджи — реализованы поверх Cloud Firestore, документоориентированной базы данных реального времени. Ключевые причины отказа от классической связки Express + PostgreSQL: (1) Firestore из коробки предоставляет потоковую (`Stream`) подписку на изменения данных, что напрямую используется в лидерборде и списке челленджей без необходимости реализовывать WebSocket-слой вручную; (2) Firebase Authentication снимает с разработчика задачу безопасного хранения паролей и управления сессиями; (3) отсутствие необходимости администрировать и оплачивать отдельный сервер и реляционную СУБД существенно снижает эксплуатационную нагрузку на проект, выполняемый одним человеком в рамках дипломной работы. При этом Node.js из исходного брифа не был полностью отброшен: он используется в виде serverless-функций Cloud Functions (`functions/index.js`) для фоновых задач, не привязанных к клиентским запросам — в частности, для периодического обновления мировых рекордов IPF (раздел 7.3).

**Push- и локальные уведомления — flutter_local_notifications вместо Firebase Cloud Messaging.** Заявленный в брифе FCM предполагает серверный триггер отправки push-уведомлений (например, «твой друг только что побил твой рекорд»). В текущей реализации уведомления (напоминания о тренировке, о заполнении опросника самочувствия) генерируются и планируются локально на устройстве средствами `flutter_local_notifications` и `timezone`, без необходимости серверной инфраструктуры для доставки сообщений. Это ограничивает набор возможных уведомлений only локальными/расписанными сценариями и отмечено как направление дальнейшего развития (раздел 10).

**Внешний AI-сервис — Groq API (модель `llama-3.3-70b-versatile`).** Для генерации и оценки тренировочных планов используется языковая модель, доступная через Groq API — облачную платформу инференса, известную крайне низкой задержкой ответа благодаря специализированному аппаратному обеспечению (LPU). Обучение собственной модели рекомендаций с нуля не рассматривалось: во-первых, у соло-разработчика нет доступа к достаточному объёму размеченных тренировочных данных для полноценного обучения; во-вторых, готовая крупная языковая модель с точно сформулированным по каждому тренировочному направлению промптом (раздел 7.1) решает задачу генерации персонализированного плана без необходимости собственной инфраструктуры машинного обучения — подход, прагматичный для инженерного проекта такого масштаба.

**Визуализация и вспомогательные библиотеки.** Графики прогресса реализованы с помощью `fl_chart`, календарь тренировок — с помощью `table_calendar`, локализация — встроенным механизмом Flutter (пакеты `.arb`).

## 5.2. Architektura systemu

Система имеет клиент-серверную архитектуру со смешанной (гибридной) моделью хранения данных.

```
┌─────────────────────────────────────────────────────────────┐
│                  Мобильное приложение (Flutter)                │
│  ┌───────────┐   ┌───────────┐   ┌──────────┐   ┌──────────┐  │
│  │  screens/ │──▶│ services/ │──▶│ models/  │   │ widgets/ │  │
│  │ (UI/UX)   │◀──│ (бизнес-  │◀──│ (данные, │◀──│ (переис- │  │
│  │           │   │  логика)  │   │  JSON)   │   │ пользуемые│  │
│  └───────────┘   └─────┬─────┘   └──────────┘   └──────────┘  │
└────────────────────────┼──────────────────────────────────────┘
                          │
        ┌─────────────────┼───────────────────┐
        ▼                 ▼                    ▼
┌───────────────┐ ┌──────────────┐   ┌──────────────────┐
│ SharedPrefs    │ │ Firebase     │   │ Внешние API       │
│ (локально):    │ │ Firestore +  │   │ • Groq LLM        │
│ Exercise,      │ │ Auth:        │   │   (генерация плана)│
│ Workout,       │ │ users,       │   │ • OpenPowerlifting │
│ WorkoutHistory,│ │ user_stats,  │   │   (мировые рекорды,│
│ WellnessEntry  │ │ friends,     │   │   через Cloud      │
│                │ │ challenges   │   │   Functions)       │
└───────────────┘ └──────┬───────┘   └────────┬──────────┘
                          ▼                    │
                  ┌──────────────┐             │
                  │ Cloud         │◀────────────┘
                  │ Functions     │
                  │ (Node.js,     │
                  │ scheduler +   │
                  │ https)        │
                  └──────────────┘
```

Приложение построено по слоистой архитектуре: `models/` содержат неизменяемые классы данных с сериализацией (`toJson`/`fromJson`), `services/` инкапсулируют бизнес-логику и обращения к внешним источникам данных (24 сервиса), `screens/` отвечают за представление и пользовательское взаимодействие (34 экрана), `widgets/` — переиспользуемые компоненты интерфейса. Слой `services` расширяет `ChangeNotifier`, что делает его совместимым с моделью реактивности Provider: изменение данных в сервисе автоматически вызывает перестроение подписанных на него виджетов.

Данные разделены на две категории по принципу «где действительно нужна облачная синхронизация»: тренировочные данные (упражнения, программы, история тренировок, опросник самочувствия) хранятся локально и не требуют сети для основного сценария использования; данные, значимые для нескольких пользователей одновременно (профиль для лидерборда, заявки в друзья, статус челленджей), синхронизируются через Firestore в реальном времени.

## 5.3. Model danych

**Локальные модели (SharedPreferences, сериализация JSON):**
- `Exercise` — упражнение: название, описание, сложность, список задействованных мышечных групп с ролью (основная/вторичная/стабилизатор — используется трекером восстановления, раздел 6.4).
- `Workout` / `WorkoutExercise` — тренировочная программа и входящие в неё упражнения с целевым числом подходов, повторений, весом и опциональным альтернативным упражнением.
- `TrainingPlan` / `ScheduledWorkout` — расписание тренировок с поддержкой периодичности: каждая запись хранит дни недели, частоту в неделях и смещение недели, что позволяет реализовывать не только простое «через день», но и чередующиеся схемы (например, программа A/B через неделю).
- `WorkoutHistory` / `WorkoutSession` / `ExerciseResult` — завершённая тренировка: дата, длительность, результаты по каждому упражнению (фактически выполненные подходы и повторения).
- `WellnessEntry` — запись опросника самочувствия: временная метка и набор числовых ответов на вопросы.
- `AppSettings` — пользовательские настройки (тема, язык, приватность).

**Облачные коллекции (Cloud Firestore):**
- `users/{userId}` — профиль пользователя, с подколлекциями `friends`, `workouts`/`workout_sessions` (реплика для доступа друзьями в рамках челленджей), `achievements`, `wellness_entries`.
- `user_stats` — агрегированная статистика для лидерборда (число тренировок, суммарный поднятый вес, текущая серия, персональные рекорды по упражнениям, флаг скрытия профиля).
- `friendRequests` — заявки в друзья (отправитель, получатель, статус).
- Коллекция с кешированными мировыми рекордами IPF, обновляемая по расписанию Cloud Function (раздел 7.3).

## 5.4. Bezpieczeństwo i prywatność danych

Аутентификация реализована через Firebase Authentication (email/пароль); ни один пароль или иной секрет не хранится в коде приложения или локальном хранилище. Доступ к данным в Firestore регулируется декларативными правилами безопасности (`firestore.rules`), построенными на принципе владения (`isOwner`): пользователь может читать и изменять только собственные данные, за исключением специально предусмотренных случаев. В частности, подколлекции `workouts` и `workout_sessions` открыты на чтение для друзей пользователя — это осознанное решение, обеспечивающее корректный подсчёт результатов в системе челленджей (раздел 7.2), где для сравнения нужны фактические тренировочные данные другого участника. Опросник самочувствия (`wellness_entries`), напротив, полностью приватен и не открывается даже друзьям. Дополнительно предусмотрен явный пользовательский переключатель `isProfileHidden`, скрывающий профиль из публичных запросов лидерборда независимо от факта дружбы.
